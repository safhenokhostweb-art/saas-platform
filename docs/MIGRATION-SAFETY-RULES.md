# قوانین امنیت مایگریشن — Module Update Safety

> **هدف:** اطمینان از اینکه بروزرسانی ماژول‌ها هرگز دادهٔ مشتری را حذف یا خراب نکند.

---

## ۱. اصول کلی

### ۱.۱ افزودنی بودن (Additive Only)

- **ترجیح:** همیشه ستون و جدول اضافه کن؛ ستون حذف نکن.
- **ممنوع:** `dropColumn`، `dropTable` روی جداولی که دادهٔ مشتری دارند.
- **استثنا:** اگر حذف ضروری است، ابتدا داده را به جدول/ستون جدید منتقل کن، سپس در مایگریشن بعدی حذف کن.

### ۱.۲ سازگاری معکوس (Backward Compatibility)

- ستون‌های جدید باید `nullable()` یا `default()` داشته باشند تا کد قدیمی بدون خطا کار کند.
- تغییر نوع ستون (مثلاً string به json) خطرناک است؛ ترجیحاً ستون جدید بساز و داده را منتقل کن.

### ۱.۳ بررسی قبل از تغییر

```php
// قبل از تغییر جدول، وجود آن را چک کن
if (!Schema::hasTable('module_xyz')) {
    return;
}

// قبل از تغییر ستون
if (!Schema::hasColumn('module_xyz', 'old_column')) {
    return;
}
```

## ۲. ساختار ماژول و نسخه‌گذاری

### ۲.۱ جداول پلتفرم (saas-platform)

| جدول | نقش |
|------|-----|
| `modules` | رجیستری ماژول‌ها؛ فیلد `version` (semver) |
| `module_releases` | تاریخچهٔ نسخه‌ها برای patch-based updates؛ `module_id`، `version`، `release_type`، `changelog`، `distributed_at` |
| `site_modules` | ماژول‌های هر سایت (tenant-aware)؛ فیلد `installed_version`، `version_reported_at` |

### ۲.۲ فرمت نسخه

- از **Semantic Versioning** استفاده کن: `MAJOR.MINOR.PATCH` (مثلاً `1.2.3`).
- `MAJOR`: تغییر ناسازگار (مثلاً حذف ستون)
- `MINOR`: قابلیت جدید سازگار
- `PATCH`: رفع باگ، بدون تغییر ساختار

### ۲.۳ نام‌گذاری مایگریشن‌های ماژول

در **customer-site**، مایگریشن‌های مربوط به یک ماژول را با پیشوند مشخص کن:

```
2026_02_26_100000_module_blog_add_excerpt_column.php
2026_02_26_100001_module_shop_add_discount_type.php
```

این کار ردیابی و rollback را ساده‌تر می‌کند.

---

## ۳. جریان بروزرسانی امن

1. **پلتفرم:** نسخهٔ ماژول در `modules.version` یا `module_releases` به‌روز می‌شود.
2. **مایگریشن:** فقط تغییرات افزودنی؛ بدون `drop` روی دادهٔ مشتری.
3. **تست:** مایگریشن را روی کپی دیتابیس واقعی تست کن.
4. **توزیع:** `SiteUpdate` (قالب) یا `ModuleRelease` (ماژول) ثبت می‌شود؛ API بروزرسانی فقط برای سایت‌های با پشتیبانی فعال پاسخ می‌دهد.
5. **گزارش نسخه:** customer-site نسخه‌های نصب‌شده را با `POST /api/updates/report-versions` به پلتفرم گزارش می‌دهد؛ در `site_modules.installed_version` ذخیره می‌شود.
6. **سایت مشتری:** مایگریشن اجرا می‌شود؛ در صورت خطا، rollback دستی با بکاپ.

---

## ۴. جداسازی دادهٔ مشتری از منطق ماژول

- دادهٔ تولیدشده توسط مشتری (مثلاً مطالب، محصولات، سفارشات) در جداول مشخص ذخیره می‌شود.
- تنظیمات ماژول (config) را در جداول جدا از دادهٔ محتوایی نگه دار.
- مایگریشن ماژول نباید به جدول‌های محتوای مشتری `drop` یا تغییر ساختار ناسازگار بزند.

---

## ۵. Rollback

- هر مایگریشن باید متد `down()` معتبر داشته باشد.
- `down()` باید عملیات `up()` را به‌صورت معکوس انجام دهد.
- قبل از rollback در production، حتماً بکاپ بگیر.

---

## ۶. چک‌لیست قبل از merge مایگریشن

- [ ] آیا مایگریشن فقط افزودنی است؟
- [ ] آیا ستون‌های جدید nullable یا دارای default هستند؟
- [ ] آیا `Schema::hasTable` / `Schema::hasColumn` برای تغییرات حساس استفاده شده؟
- [ ] آیا `down()` تست شده؟
- [ ] آیا نسخهٔ ماژول در `modules.version` به‌روز شده؟
