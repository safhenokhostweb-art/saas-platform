## ۱. ممیزی وضعیت فعلی

### ۱.۱ saas-platform (پنل مدیر اصلی)

| جنبه | وضعیت | توضیح |
|------|--------|--------|
| **ساختار** | ✅ خوب | Laravel استاندارد؛ Controller، Model، Service؛ بدون پوشهٔ Modules مجزا. |
| **دیتابیس** | ✅ خوب | جداول sites، site_modules، site_module_features، platform_licenses، products، invoices، support_plans، site_support_subscriptions؛ مایگریشن‌ها منظم. |
| **ماژول‌ها** | ✅ داده‌محور | تعریف در `modules` و `module_features`؛ فعال/غیرفعال per-site در `site_modules` و `site_module_features`. |
| **لایسنس** | ✅ پیاده شده | LicenseServerService (issue/validate)، API `/api/license/validate`؛ domain و expiry چک می‌شود. |
| **پشتیبانی** | ✅ پیاده شده | `Site.support_expires_at`؛ محصول نوع support_plan؛ OrderFulfillmentService تمدید می‌کند. |
| **بروزرسانی** | ⚠️ ناقص | API `/api/updates/check` فقط لایسنس را چک می‌کند؛ **چک support_expires_at برای اجازهٔ دریافت بروزرسانی وجود ندارد.** |
| **فروشگاه پلتفرم** | ✅ | Product (license_template, module_addon, support_plan)، CartService، Zarinpal، Checkout، Fulfillment. |
| **UI** | ⚠️ ناهماهنگ با customer-site | Tailwind 3، Vite، Vazirmatn، RTL؛ `platform-styles` و CSS vars از PlatformSettings. |
| **SEO** | ⚠️ جزئی | سرویس‌های SeoEngine، MetaBuilder، SchemaBuilder، SitemapService وجود دارند؛ فقط در ProductObserver استفاده شده و Product مدل morph seoMeta ندارد؛ صفحهٔ ثابت (page/show) متا و OG دستی دارد. |
| **کد** | ✅ | Service Layer موجود؛ Repository استفاده نشده (فعلاً لازم نیست). |

### ۱.۲ customer-site (قالب سایت مشتری)

| جنبه | وضعیت | توضیح |
|------|--------|--------|
| **ساختار** | ✅ | Laravel؛ Install، Front، Admin؛ بدون API جدا. |
| **دیتابیس** | ✅ | licenses، pages، posts، categories، products، orders؛ جدا از پلتفرم. |
| **ماژول‌ها** | ⚠️ دو منبع | فعال/غیرفعال با **config + .env** (MODULE_BLOG_ENABLED، MODULE_SHOP_ENABLED)؛ لیست ماژول‌های مجاز از **لایسنس** می‌آید ولی **کنترل ران‌تایم فقط با env است** نه با دادهٔ لایسنس. |
| **لایسنس و UX** | ✅ | LicenseActivationService، GET site-config؛ PlatformUxService و platform-styles برای پنل و auth. |
| **بروزرسانی** | ✅ | UpdateCheckService و دکمهٔ «بررسی بروزرسانی» در ادمین. |
| **UI فرانت** | ❌ ناهماهنگ | قالب پیش‌فرض: **CSS اینلاین**، بدون Vite در layout، فونت Tahoma؛ **از CSS vars پلتفرم در فرانت استفاده نمی‌شود.** |
| **UI ادمین** | ⚠️ | platform-styles + اینلاین؛ Vazirmatn لینک شده؛ ساختار مشابه پلتفرم ولی فاصله/رادیکال/رنگ‌ها یکسان نیست. |
| **SEO** | ❌ ضعیف | فقط `@yield('title')` و meta_title در مدل‌ها؛ **بدون meta description در head**؛ بدون sitemap؛ بدون JSON-LD؛ بدون canonical یکسان؛ OG فقط در یک صفحهٔ خاص نیست در layout. |
| **Tailwind** | ⚠️ نسخه متفاوت | Tailwind 4 و @theme با فونت Instrument Sans (برای فارسی نامناسب). |

### ۱.۳ خلاصه شکاف‌ها

- **بروزرسانی فقط در دورهٔ پشتیبانی:** در API بروزرسانی پلتفرم، شرط `support_expires_at >= now` اعمال نشده است.
- **ماژول در customer-site:** باید «فعال بودن» ماژول از لیست ماژول‌های لایسنس + تنظیم پلتفرم بیاید، نه فقط از .env (env برای fallback یا override).
- **یکپارچگی UI:** هر دو پروژه باید از یک سیستم طراحی (رنگ، فاصله، تایپو، کامپوننت) و در صورت امکان یک نسخه Tailwind استفاده کنند؛ فرانت customer-site باید از متغیرهای تم پلتفرم استفاده کند.
- **SEO:** متا تگ خودکار، JSON-LD، sitemap، canonical، OpenGraph در هر دو پروژه به‌صورت یکپارچه و قابل نگهداری.
- **عملکرد:** Lazy loading، بهینه‌سازی asset، کش (صفحات، API، sitemap).

## ۲. ماژول‌های پیشنهادی برای بازار ایران

ماژول‌های **فعلی** در پلتفرم: **shop**، **installment** (با فیچرهای azki_vam، tara، snap_pay).

ماژول‌های **پیشنهادی** برای اضافه شدن (به‌صورت تدریجی):

| ماژول | slug پیشنهادی | کاربرد | اولویت |
|--------|----------------|--------|--------|
| وبلاگ | `blog` | قبلاً در customer-site با config؛ در پلتفرم به‌صورت ماژول رسمی و قابل فعال/غیرفعال per-site | بالا |
| قرار ملاقات / نوبت | `appointment` | نوبت‌دهی برای خدمات (کلینیک، سالن، مشاوره) | بالا |
| فرم‌ساز پیشرفته | `forms` | فرم‌های داینامیک و ارسال (قسمتی در پلتفرم هست؛ می‌توان به سایت مشتری هم داد) | متوسط |
| اعلان / SMS | `notify` | ارسال SMS/اعلان (وابسته به درگاه SMS ایرانی) | متوسط |
| گزارش و داشبورد ساده | `reports` | گزارش فروش، بازدید، سفارش (خلاصه) | متوسط |
| چند شعبه / انبار | `multibranch` | انبار و شعبه برای فروشگاه | پایین |
| تقویم شمسی | `jalali` | نمایش و ورود تاریخ شمسی در همهٔ بخش‌ها (الان با Helper هست؛ می‌توان به‌صورت ماژول و یکپارچه کرد) | پایین |

**توصیه:** ابتدا **blog** را به‌عنوان ماژول در پلتفرم تعریف کنید و در customer-site فعال/غیرفعال آن را از **site-config / لایسنس** بگیرید تا دو منبع (env و پلتفرم) یکی شود. بقیهٔ ماژول‌ها پس از تثبیت معماری و طراحی اضافه شوند.

## ۳. معماری خرید و لایسنس و پشتیبانی

### ۳.۱ وضعیت فعلی (خلاصه)

- **خرید یک‌بار:** لایسنس قالب، ماژول افزودنی، پلن پشتیبانی به‌صورت Product و Invoice و Fulfillment پیاده شده است.
- **لایسنس:** اعتبارسنجی با domain و expiry؛ ماژول‌ها و support_expires_at از Site برگردانده می‌شود.
- **پشتیبانی:** support_expires_at روی Site؛ تمدید با خرید محصول support_plan.
- **بروزرسانی:** API فقط لایسنس را چک می‌کند؛ محدودیت زمانی پشتیبانی اعمال نمی‌شود.

### ۳.۲ تغییر پیشنهادی: محدود کردن بروزرسانی به دورهٔ پشتیبانی

- در **Api\UpdateController** بعد از اعتبار لایسنس و بارگذاری `$site`:
  - اگر `$site->support_expires_at` خالی یا منقضی شده باشد، پاسخ با `allowed: false` و `error: 'support_expired'` برگردانده شود و `latest_version` / `update_available` اصلاً برگردانده نشود (یا فقط `update_available: false`).
- در **مستندات** (PROJECT-GUIDE و implementation-guides) صریحاً ذکر شود: «دریافت بروزرسانی فقط در بازهٔ فعال پشتیبانی (support_expires_at) امکان‌پذیر است.»

بقیهٔ جریان (صدور لایسنس، تمدید پشتیبانی با خرید، Fulfillment) بدون تغییر باقی بماند.

### ۳.۳ یکپارچگی ماژول در customer-site

- **منبع حقیقت:** پلتفرم (site_modules برای هر site؛ خروجی license/validate و site-config).
- **پیشنهاد:** در customer-site:
  - اگر لایسنس معتبر وجود دارد، لیست ماژول‌های فعال از **License (modules)** یا از **site-config** خوانده شود.
  - متدهایی مثل `SiteHelper::blogEnabled()` و `shopEnabled()` اول از این لیست (و در صورت نیاز از کش site-config) استفاده کنند؛ در صورت نبود لایسنس یا خطا، fallback به **config/modules.php + .env**.
- با این کار، فعال/غیرفعال کردن ماژول از پلتفرم بدون تغییر دستی .env در سایت مشتری اعمال می‌شود.

## ۴. سیستم طراحی یکپارچه (UI/UX)

### ۴.۱ اهداف

- یکسان‌سازی ظاهر **پلتفرم** و **سایت مشتری** (پنل و در صورت امکان فرانت).
- کاهش نیاز به پشتیبانی با UI قابل فهم و یکدست.

### ۴.۲ توکن‌های طراحی پیشنهادی (مشترک)

این مقادیر در **پلتفرم** در تنظیمات تم/فونت ذخیره می‌شوند و از طریق **site-config** و **platform-styles** به سایت مشتری می‌روند. مقادیر پیش‌فرض زیر به‌عنوان پایه پیشنهاد می‌شوند:

| توکن | متغیر CSS (فعلی/پیشنهادی) | پیش‌فرض | کاربرد |
|------|----------------------------|---------|--------|
| رنگ اصلی | `--platform-primary` | `#4f46e5` | برند، لینک‌ها، دکمهٔ اصلی |
| رنگ ثانویه | `--platform-secondary` | `#6366f1` | hover، accent |
| پس‌زمینه منو | `--platform-menu-bg` | `#ffffff` | نوار بالا / سایدبار |
| متن منو | `--platform-menu-text` | `#374151` | آیتم‌های منو |
| لینک فعال | `--platform-menu-link-active` | `#2563eb` | آیتم فعال |
| پس‌زمینه سایدبار | `--platform-sidebar-bg` | `#ffffff` | پنل ادمین |
| دکمه اصلی | `--platform-button-primary-bg` / `-text` | `#4f46e5` / `#fff` | دکمه‌های اصلی |
| فونت متن/عنوان | `--platform-font-body` / `-title` | Vazirmatn | همهٔ متن‌ها |
| فاصلهٔ پایه | — | ۴px (۱ واحد = 4px) | spacing یکسان |
| شعاع گوشه | — | 0.5rem (۸px) برای کارت و دکمه | border-radius |

### ۴.۳ هماهنگی فنی

- **Tailwind:** یکسان‌سازی روی **یک نسخه** (پیشنهاد: Tailwind 3 در هر دو تا زمانی که پلتفرم به 4 مهاجرت نکرده) تا کلاس‌ها و رفتار یکسان باشد. در customer-site فعلاً Tailwind 4 با فونت Instrument Sans استفاده شده؛ برای فارسی باید فونت به Vazirmatn (یا همان توکن پلتفرم) تغییر کند و از همان CSS vars در فرانت استفاده شود.
- **فرانت customer-site:**
  - در layout فرانت (themes/default) استفاده از **همان** `partials/platform-styles` (یا خروجی مشابه) تا رنگ و فونت با پلتفرم و پنل یکسان باشد.
  - ترجیحاً استفاده از Vite + یک فایل CSS مشترک (مثلاً با همان توکن‌ها) به‌جای فقط CSS اینلاین.
- **کامپوننت‌های مشترک (اختیاری):** در صورت تمایل، می‌توان یک پکیج Blade/آدرس مشترک برای دکمه، کارت، فرم، alert تعریف کرد تا در هر دو پروژه استفاده شود؛ در فاز اول می‌توان فقط با توکن‌ها و کلاس‌های یکسان جلو رفت.

### ۴.۴ مستندات

- یک سند **DESIGN-SYSTEM.md** (در هر دو پروژه یا فقط در پلتفرم) شامل جدول توکن‌ها، نمونهٔ استفاده در Blade و قوانین (مثلاً فقط از توکن‌ها برای رنگ استفاده شود).

## ۵. سیستم SEO خودکار

### ۵.۱ اهداف

- متا تگ خودکار (title، description)
- دادهٔ ساختاریافته (JSON-LD)
- sitemap خودکار
- بهینه‌سازی slug
- OpenGraph و Twitter Card
- Canonical URL

### ۵.۲ پلتفرم (saas-platform)

- **وضعیت:** SeoEngine، MetaBuilder، SchemaBuilder، SitemapService وجود دارند؛ استفاده محدود (Product بدون morph seoMeta).
- **پیشنهاد:**
  - مدل‌های قابل ایندکس (Page، Product در فروشگاه پلتفرم در صورت وجود صفحهٔ عمومی) به **morph relation seoMeta** و در صورت نیاز فیلدهای meta_title، meta_description مجزا مجهز شوند.
  - در layout اصلی (صفحهٔ ثابت، فروشگاه، و غیره) یک **Blade partial** یا View Composer برای رندر متا و JSON-LD از روی مدل فعلی (یا از SeoMeta) استفاده شود.
  - Sitemap: روت عمومی مثلاً `GET /sitemap.xml` که SitemapService را صدا بزند و خروجی را برگرداند؛ در صورت وجود چند نوع URL، sitemap index + sitemapهای جداگانه.
  - قوانین: تمام URLهای عمومی canonical؛ در صورت تکراری بودن محتوا noindex.

### ۵.۳ سایت مشتری (customer-site)

- **وضعیت:** فقط title از مدل؛ meta_description و OG در layout یکپارچه نیست.
- **پیشنهاد:**
  - در **layout فرانت** (themes/default):
    - یک بلوک `@stack('meta')` یا `@yield('meta')` برای متا و OG و Twitter.
    - یک بلوک `@stack('json-ld')` برای اسکریپت JSON-LD.
  - برای هر نوع صفحه (خانه، صفحه ثابت، مطلب وبلاگ، محصول، لیست وبلاگ/فروشگاه):
    - مقداردهی متا (title، description) از مدل (meta_title، meta_description یا fallback به title و خلاصه).
    - OG: type، title، description، url، locale (fa_IR)، image در صورت وجود.
    - Canonical: url()->current() یا URL نهایی بدون query.
  - **Sitemap:** روت `GET /sitemap.xml` (یا /sitemap_index.xml) با کنترلر/سرویس که صفحات، مطالب، محصولات (و در صورت نیاز دسته‌ها) را از دیتابیس بخواند و خروجی XML تولید کند.
  - **JSON-LD:** حداقل Organization (برای صفحهٔ اصلی)، WebPage/Article برای مطالب و صفحات، Product برای محصولات.
  - **Slug:** اطمینان از یکتا بودن و استفاده از کاراکترهای مجاز (حروف، اعداد، خط تیره)؛ در صورت نیاز یک Helper برای تولید slug از عنوان.

### ۵.۴ پیاده‌سازی تدریجی

- فاز ۱: متا و OG و canonical در layout مشتری + سرویس/کلاس کوچک برای تولید آرایهٔ متا از مدل.
- فاز ۲: sitemap در customer-site؛ سپس در پلتفرم در صورت نیاز.
- فاز ۳: JSON-LD برای صفحهٔ اصلی و نوع محتوا (Article، Product).
- فاز ۴: یکپارچه‌سازی با مدل SeoMeta در پلتفرم و در صورت تمایل در سایت مشتری برای صفحهٔ سفارشی.

## ۶. بهینه‌سازی عملکرد

### ۶.۱ پیشنهادها (بدون افزودن پکیج غیرضروری)

|------|--------|------------|

| **کش سیمپ** | کش ۱ ساعته یا روزانه برای sitemap.xml | مشابه |
| **تصاویر** | lazy loading با `loading="lazy"` و در صورت امکان dimensions برای جلوگیری از layout shift | همان |
| **اسکریپت/استایل** | Vite در production؛ chunk splitting؛ به‌حداقل رساندن اینلاین در layout | همان |
| **دیتابیس** | ایندکس روی slug، published_at، site_id، license_key_hash و غیره طبق کوئری‌های پرکاربرد | ایندکس روی slug و وضعیت انتشار |
| **صفحات عمومی** | در صورت نیاز کش صفحه برای صفحهٔ ثابت/وبلاگ (با TTL کوتاه یا cache tags) | همان |

### ۶.۲ هزینه

- بدون پکیج اضافی؛ استفاده از کش Laravel (file/redis) و امکانات استاندارد.

## ۷. بهبودهای لاراول و ساختار کد

### ۷.۱ وضعیت فعلی

- **Service Layer:** در هر دو پروژه استفاده می‌شود (LicenseServerService، OrderFulfillmentService، PlatformUxService، LicenseActivationService، UpdateCheckService و غیره).
- **Repository:** استفاده نشده؛ برای پیچیدگی فعلی ضروری نیست.

### ۷.۲ پیشنهاد

- **نگه داشتن ساختار فعلی:** Controller → Service → Model.
- **استفاده از Repository** فقط در صورت رشد زیاد منطق کوئری یا نیاز به تعویض منبع داده؛ در غیر این صورت از Eloquent مستقیم در Service استفاده شود.
- **Form Request** برای درخواست‌های API و فرم‌های مهم (لایسنس، checkout، تنظیمات) برای اعتبارسنجی و خوانایی.
- **سیاست (Policy)** برای دسترسی به منابع حساس (مثلاً سایت، لایسنس، محصول) در پلتفرم.
- **مستندسازی:** به‌روز نگه داشتن PROJECT-GUIDE و implementation-guides با هر تغییر در API و مسیرها.

## جمع‌بندی

- **معماری فعلی** برای لایسنس، پشتیبانی و فروش یک‌بار مناسب است؛ تنها اصلاح مهم، **محدود کردن دریافت بروزرسانی به دورهٔ پشتیبانی** و **یکپارچه کردن منبع ماژول در customer-site** است.
- **ماژول‌های جدید** برای بازار ایران به‌صورت تدریجی و با اولویت blog، appointment و forms پیشنهاد شد.
- **UI/UX** با تعریف توکن‌های طراحی و استفادهٔ واقعی از platform-styles در فرانت customer-site و یکسان‌سازی Tailwind/فونت هماهنگ می‌شود.
- **SEO** با متا خودکار، OG، canonical، sitemap و JSON-LD در هر دو پروژه به‌صورت مرحله‌ای قابل اضافه شدن است.
- **عملکرد** با کش و lazy loading و بهینه‌سازی asset بدون پکیج اضافی بهبود می‌یابد.
- **کد** با همان الگوی Service و بدون Repository اضافی تا زمانی که لازم شود، نگه داشته می‌شود.

پس از تأیید این پیشنهاد، می‌توان از **مرحله ۱** شروع کرد و هر مرحله در یک یا چند کامیت جدا و قابل رول‌بک تحویل داده شود.
