# Phase 6 — Motion Graphics SaaS Integration Activation: Mandatory Pre-Implementation Audit

Produced before any Phase 6 code changes, per task instruction. Synthesizes three independent read-only investigations: License/Entitlement system, Deployment Engine/site provisioning, and Module registration/RBAC/Template Builder. All file:line references were spot-checked directly against the current repository state (not taken on agent report alone).

## 1. Current SaaS Integration Points

- **Host adapter boundary (Phases 1-5, already built):** `app/Modules/MotionGraphics/*` — Contracts, DTOs, Adapters, Bindings, Services, Support, Exceptions, Models — wired through `App\Providers\MotionGraphicsAdapterServiceProvider`, registered last in `config/app.php`'s `providers` array (config/app.php:176-177), immediately after `App\Providers\InfrastructureServiceProvider` (which itself must bind first). This is the *only* currently-registered piece of Motion Graphics on the host.
- **Standalone module (not integrated):** `packages/saas-platform/modules/motion-graphics` is reached only via a raw root `composer.json` PSR-4 autoload rule (`"SaaSPlatform\\Modules\\MotionGraphics\\": "packages/saas-platform/modules/motion-graphics/src/"`). It is **not** a Composer path-repo dependency like the four real packages (tickets, forms, education, seo-advanced — see `composer.json:10-30,47-50`, each installed under `vendor/saas-platform/modules-*` with `extra.laravel.providers` triggering auto-discovery). Motion Graphics' own `composer.json` has no `extra.laravel.providers` key, and its `MotionGraphicsServiceProvider` is never registered anywhere (not in `config/app.php`, not via discovery) — confirmed still true.
- **Feature flag:** `motion_graphics_integration` in `packages/saas-platform/core-utils/config/feature-flags.php`, default `false`, consulted via `HasTenantContext::hasFeature()` (global config short-circuits before any per-tenant `features` JSON column is consulted).
- **Persistence:** 5 Motion-owned tables from Phase 3 (`template_asset_packages`, `site_asset_packages`, etc.) already migrated; fully independent of any platform table.
- **No `modules` table row exists** for `motion-graphics` (not present in `database/seeders/ModuleSeeder.php` or anywhere else) — confirmed via direct read of `ModuleSeeder.php:1-40`.
- **No route, no controller, no public API surface** exists for Motion Graphics — confirmed unchanged through Phase 5.
- **Template Builder is real and active:** `App\Models\ThemeTemplate` (`app/Models/ThemeTemplate.php`), backed by `theme_templates` table, driven by `App\Services\ThemeBuilder\ThemeTemplateService`. Supports `site_id = null` (platform-wide) vs. per-site templates, `blocks`/`global_styles`/`demo_data` JSON, licensing, usage tracking. This is the real "Template Builder" the task audit asks about — distinct from the aspirational docs under `packages/.../motion-graphics/docs/template-builder-contract/`.

## 2. Existing Services Motion Graphics Should Consume

| Concern | Real canonical service | Notes |
|---|---|---|
| Tenant identity | `App\Services\TenantContext` (`TenantContextContract`) | Already consumed everywhere via `AbstractMotionAdapter` since Phase 1. No change needed. |
| Feature flagging | `HasTenantContext::hasFeature()` | Already consumed. Global config currently `false` and short-circuits; per-site override (`site.features` JSON) is technically wired but inert while global is non-null — relevant to the "internal test site only" requirement (see §6). |
| Module entitlement/licensing | `App\Adapters\ModuleLicenseAdapter::checkEntitlement()` → `App\Models\Module`, `App\Services\ModuleLicenseService`, `App\Services\ModuleAssignmentService` | Real, working, tested (`ModuleLicenseServiceTest`, `Wave2LicenseSecurityTest`, etc.). Traced its exact branching directly, through two layers, not one: `checkEntitlement()`'s own `isDistributionDisabled()`/`isCore()` checks (`app/Adapters/ModuleLicenseAdapter.php:34-43`), **and** `ModuleLicenseService::hasValidLicense()`'s own independent, stricter type gate (`app/Services/ModuleLicenseService.php:21-32`: `type === TYPE_CORE` → true; `type !== TYPE_PAID` → **hard false**, regardless of any `ModuleLicense` row). This second gate means a `license_required`-driven `type = internal` row (my first draft of this section) can never actually pass `hasValidLicense()` — it was a dead end, corrected after direct verification. The only type that both (a) reaches an unconditional allow and (b) stays off every *live* customer-facing surface is `type = TYPE_CORE` combined with `free_assignable = true` (to avoid `getDistributionMode()`'s catch-all `MODE_DISABLED`, which `checkEntitlement()` denies before ever reaching `isCore()`). See §4/§5 for the verified final shape. |
| Template selection | `App\Models\ThemeTemplate` / `ThemeTemplateService` | Real hook point for "Template Selected → Motion Asset Package Resolver." `ThemeTemplate::id`/`uuid` + `site_id` can key into `TemplateAssetPackageService` (already built, Phase 3). |
| Authorization pattern | None to adopt beyond what exists | See §3 — the `Permission`/`Role` RBAC tables are unpopulated and unused (no seeder, no live `hasPermission()` caller); only two ad hoc `Gate::define()` calls exist in the entire app (`access-site`, `accessWizard` — `app/Providers/AuthServiceProvider.php:18-24`), with inconsistent kebab/camel naming and no dot-namespace convention. Motion Graphics' existing `PermissionGatewayAdapter` (checking `is_admin`/`site_id === null` plus a hardcoded customer allowlist) is therefore already *consistent* with house practice, not a deviation from it. |

## 3. Existing Services Motion Graphics Must Not Duplicate

- **Deployment/provisioning pipeline** (`CustomerInstallationOrchestrator`, driver classes under `app/Services/CustomerInstallation/Drivers/*`, `ModuleDeploymentRequestService`, `CustomerInstallationPipelineJob`) — must not be reimplemented or partially re-created. Confirmed (Agent B) this pipeline is SSH/driver-based, requires an already-provisioned site with `remote_server_id`, and is structurally for a different problem (shipping code/files to a remote server) than Motion Graphics' DB-only "activate this package for this site" need.
- **License/entitlement bookkeeping** (`Module`, `ModuleLicense`, `ModuleLicenseService`, `ModuleAssignmentService`, `ModuleEntitlement`/`EntitlementLedger`) — must not be re-derived inside Motion Graphics. Where entitlement is needed, delegate to `ModuleLicenseAdapter::checkEntitlement()`.
- **RBAC tables** (`Role`, `Permission`, pivot tables) — dormant and unused elsewhere; must not be the trigger for inventing a new parallel permission system either. No action required here beyond what's already built.
- **Tenant resolution** (`TenantContext`) — already correctly consumed; do not add a second source of tenant truth.
- **Marketplace visibility/catalog logic** (`TenantMarketplaceController`, `MarketplaceModuleCatalog`, `VisibilityResolver`) — must not be duplicated or worked around with a bespoke check; Motion Graphics' `modules` row relies entirely on the existing `type`/`free_assignable` semantics those services already implement (§4) to stay off customer-facing surfaces, rather than adding a new exclusion rule anywhere.

## 4. Required Adapters

- **No new adapter classes are required for the read/authorization/tenant paths** — Phases 1-5 already built the full `AbstractMotionAdapter` fail-closed chain and it needs no changes.
- **License Gateway swap:** `App\Modules\MotionGraphics\Support\FakeMotionLicenseGateway` is replaced by `App\Modules\MotionGraphics\Support\RealMotionLicenseGateway`, a thin wrapper around `ModuleLicenseAdapter::checkEntitlement()` (already implements `ModuleLicenseServiceInterface`, already bound in the container) — this satisfies "only replace with existing canonical services." Requires one `modules` row (see §5) shaped as `type = Module::TYPE_CORE`, `free_assignable = true`, `license_required = false`. With this shape, `checkEntitlement()` reaches its `isCore()` branch and allows any active, non-retired site unconditionally — the same shape blog/shop already use. This is a **coarse, platform-wide** entitlement gate (with a real admin kill switch: `is_active = false` or `retired_at` set instantly denies it through the real system), not a per-site one — the per-site restriction is deliberately left to the feature flag (§6), not invented here as a second, duplicate gate. Verified this row is invisible on every *live* customer-facing surface: `App\Http\Controllers\Api\TenantMarketplaceController::modules()` (the only wired customer marketplace endpoint) queries `Module::paidMarketplace()` (`app/Models/Module.php:111-129`), which requires `type = TYPE_PAID` — `type = core` is structurally excluded, independent of any other flag. `App\Services\ModuleEcosystem\MarketplaceModuleCatalog`/`VisibilityResolver` were also checked and confirmed to have **no controller or route anywhere in `app/`** (grepped directly) — they are unwired, exactly like Phase 5's `DeploymentVerificationService` finding — so their theoretical "available" outcome for a `free_assignable` core module is not a live exposure today, only a documented risk (§6) if either is ever wired up later.
- **Deployment Gateway swap:** confirmed **no real canonical replacement exists** for `FakeMotionDeploymentGateway`. The only real "activation of already-installed content for a site" mechanism in the codebase is Motion Graphics' own Phase 3/4 `SiteAssetPackageActivationService::activate()` — which Motion Graphics already owns and already uses. Recommendation: **keep `FakeMotionDeploymentGateway` as the bound implementation, explicitly documented as intentional** (not a gap to be silently left) — forcing a connection to `CustomerInstallationOrchestrator`/`ModuleDeploymentRequestService` would misuse a heavyweight SSH-based pipeline built for a structurally different problem, which itself would violate the task's "do not bypass the existing deployment engine" rule in spirit (using it for something it isn't for) even while technically "connecting" to it.
- **No adapter is needed to reach `ThemeTemplate`** for the Template Builder connection — `TemplateAssetPackageService::resolveReferences()` (already made `public` in Phase 4) can be called directly with a `ThemeTemplate` id/site_id pair from a future controller/service; no new contract is required for Phase 6's scope (no controller is being added this phase either, per task's "no public API").

## 5. Migration Requirements

Confirmed existing migration strategy: standard Laravel migrations under `database/migrations/`, additive, no destructive changes seen anywhere in the 5 prior Motion Graphics migrations.

Implemented as:
- **One additive, reversible seeder entry** in `database/seeders/ModuleSeeder.php` (no schema migration needed — the `modules` table and all required columns already exist): a single `modules` row (`slug => 'motion-graphics'`, `type => Module::TYPE_CORE`, `free_assignable => true`, `license_required => false`, `marketplace_visible => false`, `is_active => true`) via `firstOrCreate` (matching the file's existing idiom for blog/shop/installment) — no schema change, no data destruction, fully reversible (delete the row).
- No `ModuleLicense` row is needed — `type = core` bypasses the license-row check entirely (§2/§4), so there is nothing per-site to grant or revoke at the licensing layer. Per-site control is entirely the feature flag's job.
- No changes to any existing table's schema. No changes to `sites`/`resellers` tables (their `features` JSON columns already exist and are what the internal-test-site enable command writes to).

## 6. Risks

- **Global feature-flag default changed from `false` to `null`** (`packages/saas-platform/core-utils/config/feature-flags.php`) so the per-site `features` JSON override becomes reachable, per `HasTenantContext::hasFeature()`'s own documented precedence order. Effective behavior for every site that never sets the key is unchanged (falls through to `?? false`); only a site whose `sites.features` JSON explicitly sets `motion_graphics_integration => true` — done exclusively via the new `motion:internal-test-site {site}` Artisan command — is enabled. This needs a regression test asserting an untouched site still resolves to disabled after the config change (in scope, §8 of the task).
- **`checkEntitlement()`'s `isCore()` branch grants unconditionally to *every* active, non-retired site**, not just the internal test site — this is intentional (§4) but means the license gateway alone provides no per-site restriction; if the feature-flag layer were ever bypassed or misconfigured, the license gateway would not catch it. This is an accepted trade-off, not an oversight — documented here so it isn't rediscovered as a "vulnerability" later without this context.
- **`VisibilityResolver`/`MarketplaceModuleCatalog` are unwired today** (no controller/route found anywhere in `app/`) but would show the `free_assignable` core `motion-graphics` row as generically "available" if either is ever wired to a real endpoint in the future, since neither considers `marketplace_visible`. Not a live risk now; flagged so a future engineer wiring either of those doesn't silently expose Motion Graphics as a customer-purchasable module.
- **No Template Builder wiring existed before this phase** — connecting `ThemeTemplate` → `TemplateAssetPackageService` is new integration surface, even though no new adapter class is required. This is a genuine, if small, expansion of what's "wired," and needs its own integration test (already in task scope).
- **Deployment Gateway remaining a fake is a deliberate, not accidental, limitation.** If a future phase needs actual cross-server delivery of Motion runtime assets, that will require new design work (not just "swap the fake for the real thing") since no real analog exists today. This should be stated plainly in Phase 6's `ROLLBACK_PLAN.md`/`INTEGRATION_RESULT.md` so it isn't misread later as an oversight.
- **RBAC is genuinely thin platform-wide**, not just for Motion Graphics — adopting `Permission`/`Role` tables now would make Motion Graphics the first real consumer of a previously-dormant system, which is out of proportion to this phase's "controlled internal usage" scope. Recommendation: do not touch RBAC tables this phase; keep the existing `PermissionGatewayAdapter` allowlist approach, which is already consistent with the rest of the app.
- **Standalone module's own ServiceProvider remains unregistered** — this phase does not need to change that (Composer package registration and `modules` table registration are confirmed fully independent mechanisms), but it means Motion Graphics' real DB-backed reads still only prove out through the module's own isolated Testbench suite, not the host suite. This is a carried-forward, known, and previously-documented limitation (Phase 2 onward), not a new one.

## Conclusion

**No architectural conflict requiring a stop was found.** All three investigation areas produced nuanced-but-solvable findings rather than blocking incompatibilities:

1. License Gateway → real swap is implemented via `ModuleLicenseAdapter`, backed by one additive `modules` seeder row (`type = core`, `free_assignable = true`) — verified directly (not inferred) that this row is unreachable through every live customer-facing endpoint, and that per-site restriction is correctly left to the feature flag rather than duplicated here.
2. Deployment Gateway → no real analog exists; the correct, non-conflicting decision is to keep it an explicitly-documented fake rather than force a connection to the wrong-shaped `CustomerInstallationOrchestrator` pipeline.
3. Module/RBAC/Template Builder → registration mechanisms are independent and additive; RBAC is dormant and doesn't need touching; a real Template Builder (`ThemeTemplate`) exists and gives a genuine, low-risk integration point.

Proceeding to implementation.
