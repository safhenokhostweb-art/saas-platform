# Phase 8 — Mandatory Pre-Implementation Audit

Produced before any Phase 8 code changes, per task instruction. Covers both repositories: `saas-platform` (this repo) and `customer-site` (`c:\laragon\www\customer-site`, a separate git working directory). Findings below are a synthesis of direct file reads (cited with path:line) and one dispatched research pass over `customer-site`; every claim was either read directly or independently verified, not inferred.

**Scope correction received mid-audit, binding for the rest of this phase:** the user has explicitly instructed that Phase 8 must not connect to any server, execute any deployment, or use SSH/cPanel/VPS/customer-server access — the SaaS deployment mechanism is an independent Deployment System outside this session's authority to execute against. Phase 8's actual deliverable is: audit, determine the integration boundary, design the adapter/contract, verify compatibility — never execute. This audit and everything built after it respects that constraint in addition to the task's own stop conditions.

## 1. Customer-site architecture

- **Module/feature bootstrap**: two independent mechanisms. (a) Composer path-repo packages (forms, tickets, core-utils) registered unconditionally via `bootstrap/providers.php`; runtime visibility gated separately by `config/modules.php` (`MODULE_*_ENABLED` env flags) + `EnsureModuleEnabled` middleware (`app/Http/Middleware/EnsureModuleEnabled.php:21-39`) on named routes (`config/module-routes.php`). (b) Nothing resembling a "drop in a Motion module" convention exists as a third pattern — Motion doesn't fit (a) cleanly since it has no admin CRUD surface of its own on the customer-site side.
- **Update/install pipeline**: push-only. Code arrives via the platform's deployment engine (git-based `deploy.sh`/`deploy.ps1`/`deploy.bat` at repo root); customer-site never pulls code. It **does** pull two things continuously: license state (`EnsureLicenseValid` middleware, revalidates every 5 min via `LicenseActivationService::syncWithPlatform()`) and, as of this audit, nothing else automated — `Admin\LicenseController::checkUpdate()` only surfaces a manual "update available" banner.
- **Rendering architecture**: a schema-driven page builder (`config/builder-elements.php` + `app/Builder/Elements/*`) is the customer-editable surface; a separate `ThemeBuilder\BlockRenderer`/`ThemeCanvasRenderer` renders header/footer/hero blocks as raw HTML strings. **A third, already-built path exists specifically for Motion**: `resources/views/components/motion/graphics.blade.php`, a Blade component (`<x-motion.graphics name="...">`) not registered as a builder-element — reachable only where a developer hand-places the tag in a theme view. This is the closest thing to a "canonical integration point" already staged in this codebase.
- **Site identity**: `config/site.php` — `platform_site_id` (`PLATFORM_SITE_ID` env, int), `platform_api_token`, `platform_url`. Licensing identity is separately a DB row, `App\Models\License::current()` (single record, `license_key`, `domain`, `expires_at`, `modules`).
- **CSP / SVG security**: **no CSP header, config, or middleware exists anywhere in customer-site** (confirmed by direct grep — zero real matches). SVG upload (theme media only, `ThemeDesignMediaController::upload()`) is accepted with only a MIME/size check — no sanitization library, no `<script>`/`onload` stripping. This is a genuine, pre-existing gap unrelated to Motion Graphics, but it means **the design must not depend on any SVG-sanitization capability that doesn't exist** — see §5 of the implementation plan.
- **Asset storage/caching**: `local`/`public`/`uploads`/`s3` disks (`config/filesystems.php`); cache store `database` by default. The Motion stub (next point) already uses `Cache::remember(..., 300, ...)`, matching the platform-config caching convention (`platform_config_cache_ttl`, default 300s).
- **A dormant Motion Graphics consumer already exists**, not built by this session:
  - `app/Services/MotionGraphics/MotionRuntimeClient.php` — `published(string $name): ?array`, gated on `License::current()->license_key`, sends `Http::withToken($license->license_key)` to `{platform_url}/api/motion/{name}` with `domain`, validates the response shape (`name`, integer `version`), filters each asset to require `url` (must start with the expected `/assets/motion/{name}/v{version}/` prefix — anti-path-traversal by construction), `sha256` (must match `^[a-f0-9]{64}$`), and `mime`, caches 300s.
  - `resources/views/components/motion/graphics.blade.php` — renders either a sandboxed `<iframe sandbox="allow-scripts" referrerpolicy="no-referrer">` (for an `text/html` entry) or a `<script type="module" integrity="sha256-...">` tag with Subresource Integrity computed from the manifest's own `sha256` (for a JS entry), `@once`-guarded (duplicate-load prevention already present).
  - **This stub currently receives nothing**: it calls `{platform_url}/api/motion/{name}` and expects a single-asset-by-name manifest; no such route exists anywhere live (the standalone module's own `motion-runtime/{slug}` route is never registered — `motion-graphics.php` config confirms every flag, including `runtime_api_enabled` and `customer_runtime_enabled`, is still `false`). The shape it expects (`{name, version, assets:[{url,sha256,mime}]}`) also does not match the task's richer suggested schema (site/template/package-scoped, with `theme_tokens`/`placement_rules`/`responsive_rules`). Treated in this phase as the canonical integration point to **extend**, not replace — see CUSTOMER_RUNTIME_ARCHITECTURE.md.
- **License verification on customer-site**: real and already wired to the Motion stub (`License::current()`) — not a new concern.

## 2. SaaS-to-customer integration boundary (this repo)

- **The canonical "customer-site calls the platform" pattern already exists and is used by ~6 other features**: `AuthenticateTenantApi` middleware (`app/Http/Middleware/AuthenticateTenantApi.php`), aliased `tenant.api`, used by `ThemeMarketplaceApiController`, `ApiLifecycleController`, `FinanceLedgerApiController`, `ThemeBundleApiController`, `ApiTenantTicketController`, `SecureAttachmentController` (`routes/api.php:70-140`). Auth is `Authorization: Bearer <license_key>` + `domain` (body/query) — **exactly** what `MotionRuntimeClient` already sends. The middleware resolves the license via `LicenseServerService::validate($licenseKey, $domain)` — checks revoked/expired/domain-mismatch/site-inactive against `PlatformLicense` (a platform-level license row, distinct from `ModuleLicense`) — and sets `$request->attributes->set('tenant_site', $site)`, a real `App\Models\Site`.
- **This is the correct, existing integration boundary for Phase 8's manifest delivery** — no new auth mechanism is needed; a new `tenant.api`-gated route reads `tenant_site` from request attributes exactly like every other tenant-facing API controller already does.
- **This boundary is distinct from `TenantContextContract`** (which resolves tenant from subdomain/reseller-detection, a different, request-lifecycle-driven mechanism used by the web/admin side). Once `tenant_site` is resolved, the controller can still call `TenantContextContract::set($site)` (the same real method Phase 6/7 already use) so `hasFeature('motion_graphics_integration')` resolves through the canonical per-site precedence — this is "use existing TenantContext," not a new mechanism, just applied at a new call site.
- **Deployment Gateway / CustomerInstallationOrchestrator**: already audited directly in Phase 6 (`docs/motion-integration-phase6-audit.md` §3-4, re-confirmed, not re-derived): the real pipeline is SSH/cPanel/SFTP/Docker/DirectAdmin driver-based, requires an already-provisioned site with a `remote_server_id`, and exists to ship *files* to a *remote server* — a different problem than "deliver a small JSON manifest to a site that already has the Motion consumer code deployed." Per the user's explicit correction, this phase does not execute against that pipeline at all, in either direction — not to test it, not to extend it. Design implication in §2 below.
- **Database reality check (this environment)**: `Site::count()` = **0**, `customer_remote_servers` = **0**, `customer_installations` = **0** in the actual (non-test) database. `customer-site/.env` declares `PLATFORM_SITE_ID=2`, i.e. this checkout is *configured* to represent a specific site — but no Site row with id 2 (or any id) currently exists to verify it against. There is no genuine, verifiable "real customer site" available in this environment today.

## 3. Determinations (task's 6 required questions)

1. **Canonical integration point**: the existing `tenant.api`-authenticated API pattern (platform side) feeding the existing, already-hardened-but-disconnected `MotionRuntimeClient` + `<x-motion.graphics>` Blade component (customer-site side). Not a new module system, not the page-builder, not the deployment pipeline.
2. **Delivery form**: a **runtime manifest** (JSON, fetched over the existing `tenant.api` HTTP channel, cached client-side) referencing already-optimized asset URLs served by the platform — not a module package (no code ships), not a raw site-asset-package dump (too much internal shape), and explicitly not carried through the file-deployment pipeline. This matches the task's own manifest schema intent.
3. **Can the existing deployment pipeline safely carry this?** No, and it doesn't need to — nothing here requires shipping files to the customer server. The manifest is fetched by code (`MotionRuntimeClient`/`<x-motion.graphics>`) *already present* in the customer-site codebase (whatever deployment mechanism most recently shipped it there, out of this phase's scope to touch). Per the user's correction, this phase does not attempt to use, replace, or exercise that pipeline in any direction.
4. **Required DB/config changes**: one small, additive, host-owned persistence model (a published, customer-fetchable manifest snapshot per site — see CUSTOMER_RUNTIME_ARCHITECTURE.md; `PackageSnapshot`, Phase 3's existing append-only audit trail, is the closest existing precedent but is shaped for internal reconstruction, not customer delivery, so a new small table is warranted rather than overloading it) plus one new `tenant.api` route. No changes to `customer-site`'s database (it doesn't have one queried here — its `License`/config already carry what's needed).
5. **Rollback strategy**: disable the site-specific feature flag (Phase 6's existing per-site mechanism, `motion:internal-test-site --disable`) and mark the published manifest row inactive — both instant, reversible, no file/deployment rollback needed since nothing was file-deployed.
6. **Is a real customer test safe right now?** **No** — for two independent, sufficient reasons: (a) the user's explicit instruction rules out any server/deployment action this phase; (b) even setting that aside, this environment has zero real Site/CustomerInstallation records, so there is no site to "explicitly select" without guessing, which the task itself forbids.

## Conclusion — no architectural blocker; real activation is out of scope this run

**No architectural or security conflict blocks building the integration.** Every piece has a real, existing, compatible anchor: `tenant.api` for transport/auth, `TenantContextContract`/Phase 6 feature-flag scoping for targeting, `ModuleLicenseAdapter`/`RealMotionLicenseGateway` for entitlement, `MotionRuntimeInstallationService`/`SiteAssetPackage` for the source data, and an already-hardened (SRI, sandboxed iframe, checksum/prefix validation, duplicate-load guard) customer-side consumer stub to extend.

**Real customer activation is explicitly out of scope for this run**, for the two reasons in §6 above — not a design flaw, a scope boundary. Per the task's own stop-condition language ("On stop: keep global and site flags OFF... report the exact root cause") and the user's explicit correction, this phase proceeds to **design and build every component up to, but not including, live activation on a real site**: the manifest contract, the platform-side API, the customer-site consumer module, the deployment-gateway *adapter design* (no execution), rendering integration, security tests, and full unit/integration/security test coverage using the same fakes-at-the-boundary discipline every prior phase used. The "Real Customer Test," live health checks, and rollback rehearsal against an actual site are documented as designed-and-ready-to-run procedures, not executed, with the exact command/steps an operator would run once a real site is designated.
